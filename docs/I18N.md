# Internationalization

Ripple's user-visible text is ready for translations without changing the wire
protocol. A missing translation always falls back to English.

## Android

English strings live in `android/app/src/main/res/values/strings.xml`. To add a
language, copy the strings that are being translated into Android's normal
locale-qualified directory, for example:

```text
android/app/src/main/res/values-es/strings.xml
android/app/src/main/res/values-fr/strings.xml
android/app/src/main/res/values-pt-rBR/strings.xml
```

Keep the resource names and format arguments (`%1$s`, `%2$d`, and so on)
unchanged. Android automatically uses the English value for any key or plural
quantity omitted by the locale. Prefer `stringResource`/`pluralStringResource`
in Compose instead of adding new UI literals.

## iOS

iOS uses the English UI literal as its localization key. Regenerate the identity
English catalog whenever literals change:

```bash
node tools/i18n/extract-ios.js
```

The dependency-free extractor scans `ios/Ripple/UI/*.swift` for literal first
arguments to `Text`, `Label`, `Button`, `TextField`, `SecureField`, and
`LabeledContent`, plus literal `navigationTitle` values. Interpolated strings are
skipped because they are not stable keys. The generated
`ios/Ripple/Resources/en.lproj/Localizable.strings` is deterministic and safe to
run repeatedly.

To start a translation, copy `en.lproj/Localizable.strings` to the corresponding
Apple language directory (for example `es.lproj`), translate only each value on
the right side, and add that locale to `CFBundleLocalizations` in `Info.plist`.
Keep the English key on the left unchanged. SwiftUI falls back to the development
language (`en`) when a translation is missing.

Dynamic/interpolated text, dates, and plurals need an explicit localized format
when they are translated; do not turn a changing runtime value into a catalog
key.

## Strings that must never be translated

These values are protocol or safety material, not prose:

- shared protocol test vectors and any byte/hex/base64 fields in them;
- the `RIPPLE-ID` and `RIPPLE-BKP` prefixes (including their `v1` tags);
- identity codes, backup blobs, node IDs, public keys, and message IDs;
- 12-digit safety codes.

Changing any of those values would break interoperability or identity
verification. Labels *around* them may be translated. Translation-only changes
must not modify `PROTOCOL.md`, `protocol/test-vectors.json`, either app's vector
copy, or `tools/protocol/`.
